# Implementation contract

Local Python 3.11+ FastAPI application, SQLite persistence, vanilla ES module frontend served from `static/`. Run via `python run.py`, bound to 127.0.0.1:8000. No Node build step.

## Shared state

`backend/db.py` exports `get_state() -> dict`, `mutate_state(callback) -> Any` (transactional synchronous callback receiving mutable state, persists changes, returns callback result), `initialize()`, and `DATA_DIR: Path`. State keys:

- `profile`: `{name,email,phone,location,headline,website,summary}`
- `items`: `[{id,kind,title,organization,start,end,original,enhanced,confirmed}]`, kind experience/project/education/publication. `original` may be empty. Imported items hold the CV's own wording in `original` with an empty `enhanced`; resumes use `enhanced` only after the user reviews a rephrasing.
- `skills`: `[{id,name,confirmed,kind?,support?,evidence?,rationale?,aliases?,origin?,source_section?,category?}]`. `category` is the label the CV groups the skill under, used to group resume skills. `support` is supported/related; `origin` is resume/suggestion/manual. Imported skills record `source_section` as skills/experience/other; missing or null means unknown for older imports. Explicit skills-section evidence is prioritized for suggestions and retained through review and duplicate imports. Only confirmed skills enter resumes/matching. CV imports confirm extracted skills automatically; additional AI suggestions remain unconfirmed.
- `skill_grouping`: `{order:[group],by_name:{normalized skill name: group}}`, context groups for the My profile skill list (`backend/skill_grouping.py`), kept apart from `skills` so grouping never changes resume or matching input. `/api/state` drops it and instead adds `group` to each grouped skill and `skill_group_order` (groups that still have skills). Skills without a group are sent to `ai.group_skills` (strongest Codex model at `medium`, skills by number, existing group names to reuse); skills the model leaves out go to `Other`. Grouping starts at startup and after skill saves, CV and skill imports, suggestions, and master resume builds; after a failure, new skills wait 10 minutes. GET `/api/skill-groups` `{state,message,model,effort,running,waiting}`; POST `/api/skill-groups/regroup` regroups every skill and replaces the groups when done.
- `dismissed_skills`: additive list of normalized names excluded from automatic suggestions.
- `positions`: `[{id,name,confirmed}]`
- `preferences`: `{track: 'industry'|'academia',location,remote_only}`
- `sources`: `[{id,name,kind,url,enabled}]`, kind remotive/greenhouse/lever/camoufox/linkedin. LinkedIn defaults to disabled and is added once to preexisting workspaces by migration; canonical URL `https://www.linkedin.com/jobs/search/`.
- `jobs`: `[{id,title,company,location,url,source,description,salary,job_type,posted_at,match_score,matched_skills,status,created_at,resume?}]`; status discovered/saved/prepared/applied/archived
- `applications`: `[{id,job_id,status,created_at,updated_at,note}]`; auto-apply records add `automated:true,attempts,attempted_at,answers_key,question,url,retry,manual_retry`, with status applying/applied/needs_input/needs_sign_in/failed.
- `application_answers`: `{work_authorization,sponsorship,salary,start_date,relocation,work_arrangement,years_experience,linkedin_url,gender,race,veteran,disability,other:[{question,answer}]}`, the answers auto-apply may use.
- `auto_apply`: `{enabled,signed_in_at?}`.
- `settings`: `{provider:'codex'|'ollama'|'compatible',base_url,model,api_key}` (GET strips api_key, exposes api_key_set). Codex allows blank model for the account default and always clears API keys.
- `codex_chat`: additive `{thread_id,messages}` conversation metadata; excluded from `/api/state`, available through `/api/codex/chat`.

## Core endpoints (backend/main.py + AI services)

- GET `/api/state`: full sanitized state
- GET `/api/health`: local service readiness
- PUT `/api/profile`: complete profile object
- POST `/api/import`: multipart `file`, PDF only (other types get 415). Each page is rendered to PNG and transcribed by the AI; a model that cannot read images gets 422 before any CV content is sent. The AI returns line numbers for descriptions and fields that are verified against the CV text, so imported wording is never AI-written. Adds confirmed items, refreshes existing items with the same kind/title/organization/start instead of duplicating them, fills empty profile fields, merges confirmed CV skills; returns `{count,added,updated,skill_count,message}`
- Master resume (`backend/master_resume.py`): with the Codex provider, `/api/import` saves the CV transcript as `cv_transcript` (not returned by `/api/state`) and starts a background build with the strongest model reported by Codex `model/list` at its deepest reasoning level (pages are read by that model at low effort). The build uses the same line-reference extraction plus nesting and the CV's own `section_titles`, then replaces items whose `source` is not `manual` (legacy untagged items count as CV items), keeps manual items, merges skills, fills empty profile fields, and records `master_resume: {built_at, model, effort}`. If CV items changed during the build, nothing is replaced. GET `/api/master-resume` returns `{state,message,model,effort,started_at,running,has_cv,built}`; POST `/api/master-resume/rebuild` reuses the saved transcript. Items carry `source`: `cv` from imports, `manual` from the app or the assistant; updates keep the stored value.
- POST `/api/import/skills`: PDF only, read the same way; recovers and confirms CV skills only, preserving profile/experience; explicitly reimported CV skills can restore dismissed entries; returns `{count,skill_count,updated,message}`
- Both CV import endpoints refresh saved-job matches and invalidate tailored resumes when confirmed content changes. Imported information is ready for use immediately and remains editable. Existing unconfirmed entries outside the current import remain unchanged.
- POST `/api/items`: fields kind,title,organization,start,end,original; AI creates enhanced draft; returns item. If AI unavailable, keep original draft and show warning.
- PUT `/api/items/{id}`: fields as above plus enhanced,confirmed. When original/content fields change rerun enhancement and reset confirmed. Confirmation alone persists reviewed enhanced version.
- DELETE `/api/items/{id}`
- POST `/api/items/{id}/enhance`: retry AI wording generation and reset confirmation; failure preserves the existing item
- POST `/api/suggestions/skills`: optional `{job_id}`; typed candidates use CV skills, confirmed experience, and confirmed skills. Broader supported techniques and related unverified options carry evidence/rationale. A job description controls relevance, never applicant facts. Stale input returns 409; dismissed candidates remain excluded.
- POST `/api/suggestions/positions`: lists every job title the confirmed master resume supports (all career tracks, specializations, and supported seniority levels) as unconfirmed roles with `family`, `fit` (strong/possible), `reason`, and `origin: suggestion`; returns `{items,count,message}`. The app runs the same listing in the background with the strongest Codex model at its deepest reasoning via POST `/api/master-resume/roles`, and automatically after each master resume build. Merging keeps checked and user-added roles, refreshes titles still suggested, drops unchecked suggestions that no longer fit, and never re-suggests roles in `dismissed_positions` (unchecked roles the user removed). PUT `/api/positions` accepts round-tripped role details but keeps the saved values.
- PUT `/api/skills` and `/api/positions`: `{items:[{id?,name,confirmed}]}`; skills may round-trip display metadata, but unchanged existing records preserve server provenance. Skill review updates saved-job matches and invalidates tailored resumes when confirmations change.
- PUT `/api/preferences`: full preferences
- PUT `/api/settings`: provider,base_url,model,api_key optional (missing/empty retains stored key),clear_api_key optional
- POST `/api/settings/test`: checks configured AI and returns `{message}`
- Google XYZ wording (`backend/xyz.py`): items may carry `xyz` (description text with each bullet rewritten), `xyz_basis` (hash of the `enhanced` or `original` text it was written from), and `xyz_measured` (per bullet). Resumes render `xyz` only while `xyz_basis` matches the current wording. `ai.rewrite_xyz` runs after each master resume build at the deepest reasoning level (or via POST `/api/master-resume/xyz` for missing or outdated entries); a rewritten bullet is kept only if its numbers all appear in that entry, else the original bullet is used. PUT `/api/items/{id}/xyz` `{xyz}` stores the user's own XYZ wording. Writing XYZ invalidates tailored resumes so job matching rebuilds them. `/api/state` adds `xyz_current` to items that have XYZ wording; item updates accept and ignore the XYZ fields.
- Job matching (`backend/job_matching.py`): jobs not archived or applied, with a description and a keyword `match_score` strictly between 30 and 100, get `ai_match: {score,summary,strengths,gaps,basis,model,effort,checked_at}` from `ai.match_job` (strongest Codex model at `high`) and a tailored `resume` without a status change. `basis` hashes the confirmed master resume and the job's title and description, so a job is redone only when either changes; failures are stored as `match_error` and retried after 30 minutes. It runs one job at a time and starts automatically after jobs are added (discovery, LinkedIn search, background search, manual jobs) and after a master resume build. GET `/api/job-matching` returns `{state,message,done,total,model,effort,running,waiting}`; POST `/api/job-matching/start` starts it.
- Auto-apply (`backend/auto_apply.py`, agent in `backend/apply_agent.py`): when `auto_apply.enabled`, applies one at a time (60-120 s apart) to jobs not archived or applied that have a URL, a tailored `resume`, and a current `ai_match` (basis unchanged) of 70 or more, highest first. Each run renders the resume to a private temporary PDF, records the application as `applying`, and runs browser-use with `ChatCodex`, a chat-model adapter that sends each step to the strongest Codex model at `low` reasoning with the latest two screenshots. The agent gets only the profile, `application_answers`, and the tailored resume, and ends with `ask_user` (status `needs_input`, `question` saved) or `needs_sign_in` instead of guessing or bypassing sign-ins and checks. `needs_input` is retried when the profile or answers change (`answers_key`), `needs_sign_in` after the application browser was opened (`signed_in_at`), and `failed` after an hour up to 3 attempts. Stopped, timed-out (40 min), or restart-interrupted applications get `manual_retry` and wait for the user. Job matching also covers keyword-perfect jobs while auto-apply is on and starts auto-apply after each job. Endpoints: GET `/api/auto-apply` `{enabled,running,state,message,job,step,applied,waiting,eligible,needs_you,browser_open,blocker,stopping,next_at}`; POST `/start`, `/stop`; PUT `/answers`; POST `/applications/{id}/answer` `{answer}` (adds to `other`), `/applications/{id}/retry`; POST `/browser` `{application_id?}` opens Chrome with `data/apply-browser-profile` (409 while the agent is using it), `/browser/close`. browser-use telemetry is turned off.
- Term bags (`backend/term_bags.py`): `term_bags = {basis,bags:[{names:[CV's term, same-thing names...],phrasings:[same-skill phrasings...]}],model,built_at}` from `ai.term_bags` (strongest Codex model at `medium`) over the confirmed master CV; bags whose term isn't literally in the CV are dropped, names are deduplicated, and the bags are listed again when `basis` (confirmed entries' wording, confirmed skills, headline, summary) changes. They start at startup and after skill, entry, import, suggestion, and master resume changes; after a failure they wait 10 minutes. `term_bags.job_resume(state, job)` copies the job's resume and, per bag, when the posting uses a term the resume doesn't: if it is one of the names and the resume uses another name, the resume's names are rewritten (an abbreviation and full name are paired once in show order: summary, entries by section, skills, as "Full (ABBR)"; other spellings are replaced everywhere; plurals follow the resume's wording); otherwise the posting's phrasing is appended to the resume's skills as written, grouped with a bag term's skill group when there is one. Rewritten entry text goes in `shown`, which `resumes.resume_text` prefers, and `wording:[{from,to}]` records the changes. The job resume HTML/PDF endpoints, the ATS check, and auto-apply use it; the stored resume is unchanged. GET `/api/term-bags` `{state,message,running,stale,count,bags}`; POST `/api/term-bags/rebuild`.
- Goldmove (`backend/goldmove.py`): eligible jobs are not archived or applied, have a tailored resume and a description, and an initial score (`ai_match.score`, else `match_score`) above 30. A background worker (started at startup, after each job is tailored or matched, after term bags are listed, and after confirmations) lists each eligible job's ATS keywords and stores its report, including `ats.missing:[{term,kind,importance}]`; failures wait 30 minutes. Candidates aggregate `missing` over jobs with a current score, excluding titles, degrees, certifications, confirmed skills, and `goldmove.dismissed` (normalized names). POST `/api/goldmove/confirm` `{terms}` adds confirmed skills with `origin:"goldmove"` (or confirms an existing unconfirmed one) and appends them to every non-applied tailored resume without invalidating resumes; `job_matching.resume_key` ignores goldmove skills so matches stay current. Nothing is added without confirmation. GET `/api/goldmove` `{state,message,done,total,running,waiting,eligible,checked,dismissed,candidates:[{term,kind,jobs:[{id,title,company}],required}]}`; POST `/scan`, `/dismiss` `{terms}`, `/dismissed/clear`.
- ATS check (`backend/ats.py`): `job.ats = {terms:[{term,kind,importance,variants}],terms_basis,model,effort,listed_at,score?,score_basis?,checked_at?,failed_at?}`. `ai.ats_terms` (strongest Codex model at `medium`) lists up to 30 short search keywords from the posting; they are kept while the job's title and description are unchanged (`terms_basis`). Each check renders the job's resume PDF, reads its text back with pypdfium2, and looks each term and variant up literally (whole words, case-sensitive for terms of three letters or fewer, singular/plural and hyphen/space variations). Status is present (a form of the term that the posting itself uses is in the resume), variant (only another name is; half credit), addable (found in the confirmed master CV: profile, entries' original/enhanced wording, confirmed skills, with `wording` and `where`), or missing. Score = present weight / total weight × 100, with required = 2 and preferred = 1. Parse checks: name, email, phone, section titles (missing or nonstandard), dates, unreadable characters, page count. `/api/state` shows `ats_score` (null when the resume or posting changed) instead of `ats`. GET `/api/jobs/{id}/ats` returns the report or `{ready:false,message}`; POST `/api/jobs/{id}/ats` `{refresh?}` lists keywords when needed and returns the report; POST `/api/jobs/{id}/ats/add` `{terms?}` appends addable wording to `resume.skills` (recorded in `resume.added_keywords`). Every job not archived or applied gets a report (Goldmove's worker, three at a time), using its tailored resume or, until it has one, `resumes.build_resume(state, job)`; `score_basis` then hashes the master key instead of a resume. Each report stores `score` (resume as sent, through `term_bags.job_resume`) and `before` (the base resume without similar-term choices, `added_keywords`, or goldmove-origin skills); `/api/state` shows them as `ats_score` and `ats_before`. Cards show only these, sorted by `ats_score`; the Full match tab is `ats_score == 100`. Auto-apply runs the check before each application, adds addable keywords, and skips jobs below `auto_apply.min_ats` (PUT `/api/auto-apply/rules` `{min_ats:0-100}`; a failed check waits 30 minutes when a minimum is set and doesn't block applying when it isn't).
- POST `/api/jobs/{id}/tailor`: prepares resume using confirmed content only, saves job.resume, sets status prepared, returns `{message,resume}`
- GET `/api/jobs/{id}/resume`: printable HTML
- GET `/api/jobs/{id}/resume.pdf`: PDF generated with reportlab
- GET `/api/resume`: general printable HTML from confirmed content
- GET `/api/resume.pdf`: general PDF

## Job endpoints (backend/jobs.py exports router)

- PUT `/api/sources`: `{items:[source...]}`
- POST `/api/jobs/discover`: searches enabled sources using confirmed positions and skills; returns `{count,message,warnings:[]}`. Source failures isolated. Persist and dedupe by URL.
- POST `/api/jobs`: `{title,company,location,url,description,salary?,job_type?}` manually save job
- PATCH `/api/jobs/{id}`: `{status}`
- POST `/api/jobs/{id}/apply`: launches visible Camoufox session, fills safe common form fields and tailored PDF when available; no silent submission; `{message,application}`
- POST `/api/applications/{id}/confirm`: user confirms externally completed submission; updates job + application applied
- GET `/api/browser/status`: browser installation/session info
- POST `/api/linkedin/search`: `{keywords:'',regions:['United States','Europe'],remote_only:false,limit:10,save:true}`; keywords are optional (blank asks LinkedIn for any job title), limit is 1–25 per region, and no confirmed profile or target role is required. LinkedIn pads results with unrelated jobs, so a result is kept only when its title shares a meaningful word with the keywords or matches a confirmed target position; with blank keywords and no confirmed positions, every result is kept. Opens/reuses a visible Camoufox session and returns `{count,found,skipped,jobs,requires_action,message,search_url,warnings}`. `count` is newly saved jobs; `found` is the number of kept results; `skipped` is the number of unrelated results. `save:false` returns results without workspace persistence. Saved results are deduplicated by canonical LinkedIn job URL.
- GET `/api/linkedin/status`: `{active,busy,requires_action,search_url,message,...}` for the current search browser and its persistent profile.

## LinkedIn integration

Every LinkedIn page load waits a random gap after the previous one (4–9 s for direct searches) and is recorded, across restarts, for the page counts the background search reports. `backend/linkedin_watch.py` runs an optional in-process background search: GET `/api/linkedin/continuous` returns `{running,state,message,found,skipped,next_at,pages_last_hour,pages_today}`; POST `/api/linkedin/continuous/start` (requires a confirmed target position) and `/stop`. Each pass pages through up to 4 result pages per region for the target-position query, opens only new relevant jobs, and waits 4 hours before the next pass. Page loads are 20–30 s apart, with 5–12 minute breaks every 8–15 loads and no hourly or daily cap. It only ends when the user stops it: load failures retry after 1 minute, doubling up to 15 minutes (logged with tracebacks to the server log); a closed window is reopened; login or checkpoint pages are re-checked every 2 minutes without navigation and the search resumes once they clear; a rate limit waits 30–50 minutes; without confirmed positions it waits. It does not survive an app restart. It holds the browser lock only for each page load, so direct searches wait for that page instead of failing.

`backend/linkedin.py` provides bounded visible browser search and detail extraction, `search_linkedin(keywords, location='', remote_only=False, limit=10)`, `linkedin_status()`, and `close_linkedin()`. Blank keywords search any job title; this primitive searches the explicit location supplied by its caller. The API coordinates regional searches. A persistent Camoufox context stores cookies/browser data at `db.DATA_DIR / 'linkedin-browser-profile'`; normal closure/restart preserves the profile. No plaintext login password is recorded by the application. Login, checkpoints, and verification are handled by the user; no automatic bypass or unattended retry. Partial results and unavailable descriptions are reported through warnings.

The LinkedIn source in normal discovery searches for the confirmed target positions (one Boolean OR query within LinkedIn's 300-character keyword limit) in the preferred location, or the United States and Europe when none is set, honoring the remote-only preference, with a limit of 10 per region. Like every discovery source, it saves only jobs relevant to a target position and the location preferences, and discovery requires at least one confirmed position. The dedicated frontend modal (`#linkedin-form`) defaults to empty keywords, both regions selected, remote-only false, and limit 10 per region. An optional custom location overrides the selected region list. Search ignores saved location preferences and reads a bounded batch, not an exhaustive inventory. On `requires_action:true`, retain all form inputs, keep the modal open, and direct the user to complete the gate in the existing browser before manually submitting again. On completion, refresh the workspace, clear job filters, and navigate to jobs.

`linkedin_search.py` offers the same browser search as a standalone CLI: optional positional keywords (default blank), `--location` to replace default United States/Europe with one location, repeatable `--region` for up to five chosen regions, `--remote`, `--limit` (1–25 per region, default 10), `--output`, `--keep-open`, and `--wait-for-login`. It exports JSON without writing to SQLite. The login flag waits for explicit terminal input before retrying; normal closure preserves the browser profile.

Agent operations are in `backend/linkedin_agent.py`, with the local API and persistence in `backend/linkedin_routes.py`. They reuse the same browser and operation lock as search. Inspection returns temporary field references and structured job data; study adds bounded page-layout evidence; job reads can save or refresh local records. Filling accepts explicit text/select answers against the current document and form identity, without clicking or submitting. Snapshots expose no current field values. Gates stop operations and leave the browser open.

`linkedin_agent.py` is a provider-neutral Python HTTP client and JSON CLI for the running app; it does not own a second browser. The `/api/linkedin/agent/tools` catalog describes the available calls. Named search definitions live in the additive `linkedin_searches` workspace list, with their last-run result. `/api/linkedin/agent/jobs` searches saved LinkedIn records without a browser request or tailored resume data. See `docs/linkedin-agent.md` for schemas and usage.

Camoufox is optional dependency; show clear actionable errors if missing. Browser managers must clean up during FastAPI lifespan shutdown via `await close_linkedin()` from backend/linkedin.py and `await close_browsers()` from backend/jobs.py. Do not claim applications submitted unless confirmed. All fetched/AI text treated as untrusted content. Include practical tests. Keep networking bounded and validate external job URLs (http/https public addresses), AI URLs permit localhost by intent. Bind loopback and enforce same-origin mutating requests.
